# HTTP API «Заказа из переписки»

[OpenAPI 3.1](../contracts/openapi.yaml) описывает клиентский контракт `0.6.0` под префиксом `/api/v1`. В примерах использованы вымышленные данные. Кофейня открывается по умолчанию, клининг подключается из кабинета по опубликованному CSV.

## Просмотр

Из корня проекта на Windows с Docker Desktop в режиме Linux-контейнеров или на Linux с Docker Engine и плагином Compose v2:

```sh
docker compose config --quiet
docker compose up -d swagger
```

- [Swagger UI](http://127.0.0.1:8081/)
- [Исходная схема](http://127.0.0.1:8081/openapi.yaml)

Порт опубликован на IPv4 loopback. Swagger UI открывает локальную схему в режиме просмотра с отключёнными Try it out, внешним валидатором и настройками из строки запроса.

Остановить просмотр можно командой `docker compose stop swagger`. Проверка схемы и примеров выполняется с Node.js 22.12+ и npm 10+.

```sh
npx --yes --package=@redocly/cli@2.12.0 -- redocly lint contracts/openapi.yaml
```

[Проверка в CI](../.github/workflows/contract.yml) запускает Compose на Linux, проверяет HTML, CSS и JS, настройки Swagger UI и побайтовое совпадение отдаваемой схемы с файлом.

## Сессии и доступ

Личный аккаунт подтверждается cookie `__Host-account_session` на HTTPS. Один вход даёт доступ к заказам аккаунта в подключённых магазинах. Сначала откройте витрину и получите актуальный CSRF. После переноса гостевых заказов прежняя гостевая сессия отзывается. В закрытом профиле идентичность приходит от корпоративного OIDC-прокси. [Учётная запись](accounts.md)

Для гостя кофейни витрина выдаёт `__Host-customer_session` на HTTPS с атрибутами `HttpOnly; Secure; SameSite=Lax; Path=/`. Для локального HTTP имя — `customer_session_dev`. У остальных витрин к имени добавляется `-{slug}`. Открытие витрины создаёт сессию и предоставляет CSRF-токен.

Покупатель читает и меняет заказы своей гостевой сессии или личного аккаунта. Сначала он открывает `/s/{slug}`, затем передаёт тот же код витрины в заголовке `X-Shop`. Для обратной совместимости запросы без заголовка относятся к кофейне. Переход между витринами сохраняет доступ к активным сессиям каждого магазина. Запрос чужого объекта с действующей сессией возвращает `404`.

При передаче продавцу карточка содержит `seller_review`. Сначала это `pending`, затем `answered` с текстом ответа. Оплата блокируется до принятой правки заказа. При обработке сообщения из другой вкладки подтверждение получает `409 request_in_progress`. Состояние `fulfilled` означает действие продавца после подтверждённой оплаты или предоплаты. Оно не меняет сумму платежа и остаток.

В локальном режиме код владельца подтверждает доступ к магазину. Приложение выдаёт отдельную сессию продавца или привязывает магазин к уже открытому личному аккаунту. В закрытом режиме браузер сначала входит через корпоративный OIDC, а приложение связывает покупательскую сессию с пользователем и проверяет назначение продавца витрине. Продавец работает с заказами, каталогом и оплатой своего магазина. Публикация прайса проверяет его версию, повтор одного MCP-токена в другом профиле отклоняется. [Закрытая конфигурация](production.md)

Все POST клиентского API требуют действующей гостевой сессии, личного аккаунта или корпоративного входа, а также заголовка `X-CSRF-Token` из HTML витрины и точного совпадения `Origin` с `PUBLIC_ORIGIN`. Сервер отвечает `403` при нарушении CSRF-проверки и отправляет `Cache-Control: no-store` для ответов с данными сессий и заказов. Текст переписки и ответа отображается с экранированием.

## Заказ и оплата

1. Покупатель открывает черновик через `POST /orders` и отправляет текст через `POST /orders/{orderId}/messages`. Если агенту хватает данных, сервер проверяет предложение по каталогу и сохраняет правки одной транзакцией с повышением версии. В остальных случаях ответ содержит уточнение или передачу сотруднику.
2. Клиент показывает суммы из карточки. Кофейня начинает с 7 250 ₽ за 20 завтраков. После замены двух обычных завтраков на вегетарианские общая сумма и платёж составляют 7 350 ₽. У клининга тариф на 58 м² и чистка духовки стоят 5 300 ₽, предоплата 30% составляет 1 590 ₽, остаток — 3 710 ₽.
3. После явного согласия покупателя `POST /orders/{orderId}/payment-attempts` передаёт показанную `order_version`. Сервер сохраняет подтверждённую версию и попытку атомарно. При `409 stale_version` клиент перечитывает карточку по `GET /orders/{orderId}`, показывает отличия и запрашивает новое согласие. Смена цены до подтверждения также возвращает `stale_version` после обновления карточки.
4. Клиент читает статус по `GET` из заголовка `Location`. При `409 payment_in_progress` актуальный идентификатор доступен в карточке заказа. После успеха каждой доли сервер обновляет прогресс. Когда все доли подтверждены, заказ получает `paid` либо `deposit_received`. Остаток после предоплаты отображается в карточке. Встроенной доплаты этого остатка пока нет.

Для создания заказа и платёжной попытки используется `Idempotency-Key`, для сообщения — `client_message_id`. После сетевого сбоя клиент повторяет запрос с прежним ключом и прежними данными. Сервер проверяет доступ и CSRF до поиска повтора, а существующий успешный результат ищет до проверки текущей версии. Запись повтора сохраняется вместе с результатом, чтобы после потери HTTP-ответа клиент мог получить исходную операцию. Одна активная попытка на заказ обеспечивается той же транзакцией, которая сохраняет попытку и подтверждение версии. Новую попытку можно создать после подтверждённого отказа или отмены.

При занятом хранилище сервер возвращает `503 storage_busy` с `Retry-After` в секундах. После ожидания повторите тот же запрос с прежним ключом и телом. Тайм-аут чтения ответа модели сохраняет резерв квоты, поскольку провайдер мог обработать запрос.

Подтверждение может передать `kind: invoice`, если в развёртывании включены счета. Оба вида используют один лимит активной попытки. Счёт действует 24 часа. В карточке показывается срок, а новую оплату после истечения разрешает только подтверждённая отмена из ЮKassa. Связанный платёж сверяется отдельно по ID, сумме, валюте и статусу.

Для прямого платежа покупатель передаёт `parts` от 1 до 4, `tip_percent` из 0, 5, 10, 15 и `part_number`. Чаевые рассчитываются от суммы к оплате сейчас. Сервер сохраняет план с первой попыткой и делит итог в копейках, добавляя по копейке первым долям при остатке. Минимальная сумма доли — 1 ₽. Между долями заказ остаётся `payment_pending`. Следующий номер и сумму берите из `checkout.paid_parts + 1` и `checkout.next_kopecks`. Старые клиенты могут опустить эти поля для обычного платежа.

Через `GET /orders/{orderId}/documents` покупатель получает список подтверждённых платежей и доступные действия. Для скачивания используйте `GET /orders/{orderId}/documents/{attemptId}/{kind}`. Для почты отправьте POST на тот же путь с суффиксом `/email`, полем `recipient` и прежним ключом при повторе. `accepted` означает, что SMTP принял письмо. `unknown` оставляет исход неизвестным и повтор с тем же ключом письма не дублирует.

## Серверная интеграция с MCP ЮKassa

MCP-инструменты доступны серверному компоненту платежей через Streamable HTTP ЮKassa с учётными данными конкретного магазина. Публичный HTTP API приложения передаёт идентификатор и состояние собственной попытки. Внешние токены, идентификаторы платежей и технические ответы MCP остаются на сервере. [Документация по MCP-инструментам](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/mcp-server/tools)

- Сервер фиксирует попытку до сетевого вызова `create_payment` и отправляет сумму из сохранённого снимка. В описание платежа помещает технический уникальный номер попытки без данных покупателя.
- При известном внешнем ID сервер вызывает `get_payment` через токен витрины и сверяет ID, сумму и валюту. Подтверждённый результат однократно меняет состояние заказа. Возврат браузера, открытие ссылки и сообщение покупателя сами по себе не обновляют статус.
- Если запрос мог дойти до MCP, но ответ потерян, попытка переходит в `unknown`. Попытка, которая остаётся в `creating`, попадает в очередь сверки через 30 секунд. Пока исход неизвестен, новая оплата заблокирована. Для прямого платежа без подтверждённого ID продавец может ввести его вручную. Если ID и кандидат отсутствуют, сервер ищет точное совпадение через `get_payments_list` и повторно проверяет единственный результат через `get_payment` с токеном этого магазина. Для счёта без ID продавец указывает ID счёта. Сервер получает его через `get_invoice` и сверяет связанный платёж перед зачётом. Отсутствие однозначной записи или расхождение сохраняет блокировку.
- Обычная попытка `pending` проверяется запросом статуса из карточки покупателя. Фоновой сверки `pending` в текущей версии нет.
