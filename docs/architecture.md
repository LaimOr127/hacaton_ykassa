# Архитектура конкурсного MVP

## Границы продукта

Один веб-сервис для продавцов с формализуемым прайсом. Три способа расчёта — фиксированная цена, сумма за единицу и тариф по диапазону. Готовая LLM работает без обучения на данных магазина. При индивидуальной смете агент передаёт менеджеру собранный черновик.

## Модули и полномочия

| Модуль | Ответственность |
| --- | --- |
| Веб-приложение | Сессия покупателя и сотрудника, карточка заказа, подтверждение суммы и управление каталогом |
| Агент | Из текущего черновика, сообщения и выбранных позиций формирует типизированное предложение изменений. Спрашивает недостающие сведения |
| Каталог и расчёт | Проверяет коды и количества, рассчитывает стоимость в копейках. Предоплата в процентах округляется до ближайшей копейки, при половине — вверх. Сохраняет снимок расчёта |
| Заказы | Применяет пакет правок одной транзакцией, проверяет версию и полномочия, хранит согласованный состав и привязку к магазину |
| Платежи | Регистрирует попытку для подтверждённой версии, обращается к MCP токеном нужного магазина, сохраняет внешний ID и сверяет результат |
| Хранилище | SQLite на постоянном диске для одной реплики. В транзакциях проверяет уникальность активной попытки и повторов сообщений |

Целевой стек — Python, FastAPI, серверные HTML-шаблоны и небольшой браузерный JavaScript. Модули работают в одном процессе и используют явные границы доступа. Docker Compose запускает приложение на Linux-сервере с поддерживаемым образом и постоянным томом. База переживает пересоздание контейнера. Резервную копию SQLite формировать штатным механизмом согласованного снимка и проверять восстановление. Масштабирование на несколько записывающих реплик потребует другого хранилища или координации. Контейнер просмотра проектной схемы служит подготовительному этапу.

## Поток заказа

Покупатель отправляет сообщение с идентификатором повтора. Агент предлагает правку, сервер проверяет каталог и последнюю версию. Неоднозначность возвращает уточнение. Деньги рассчитывает приложение. При изменении прайса до подтверждения возвращается новая карточка заказа. У подтверждённой версии неизменяемые строки, суммы и доля предоплаты. Два повторных уточнения без продвижения дают покупателю выбор вручную или передачу сотруднику.

При подтверждении сервер атомарно создаёт запись попытки и фиксирует транзакцию до сетевого запроса. Сетевой вызов не удерживает блокировку базы. Единственный создатель попытки вызывает create_payment через MCP. После успешного ответа сохраняет payment_id и, при наличии, confirmation_url. Сохранённая ссылка может быть возвращена повторно владельцу заказа. После обрыва с неизвестным результатом повторная отправка на создание блокируется до сверки у продавца. Для сверки в description передаётся уникальный короткий номер попытки без персональных данных.

Для известного ID сервер вызывает get_payment, сравнивает магазин подключения, ID, сумму и валюту. При succeeded один раз отмечает «Оплачен» либо «Предоплата получена». Pending оставляет попытку в ожидании, canceled позволяет новую попытку. Старый или неожиданный результат попадает на сверку. Фразу «я оплатил», открытие ссылки и возврат браузера нельзя использовать как доказательство оплаты. Для MVP при активной ссылке редактирование согласованной версии блокируется до решения участи платежа.

## Контракты и развёртывание

Новый продавец регистрируется по коду подключения и получает кабинет со своей серверной сессией. Он публикует CSV по версии каталога и подключает собственный MCP-токен. Токен сначала проверяется через список инструментов, затем шифруется с привязкой к магазину. Серверный токен относится только к существующей кофейне. Существующие таблицы заказов сохраняются при добавлении таблиц кабинета. Покупатель получает отдельную cookie для каждой витрины, поэтому истечение одной сессии не влияет на другие.

Публичное HTTP API приложения описывает версии заказа, ошибки, авторизацию и повторы. Swagger UI открывает этот контракт. Отдельный серверный MCP-клиент подключается к официальному Streamable HTTP endpoint ЮKassa. В публичный API входят только операции приложения, необходимые покупателю и продавцу. Автогенерируемую схему FastAPI и проектный контракт сверить в CI при первой реализации, затем поддерживать один авторитетный контракт.

Для готового релиза нужны воспроизводимая сборка приложения, один Compose-запуск без локального Python, непривилегированный пользователь, healthcheck и постоянный том. Тестовые секреты каждого магазина поступают из защищённой конфигурации. В README релиза указываются переменные без значений, способ проверки статуса, доступ к Swagger и сценарий восстановления после перезапуска. Для боевого использования проверяются фискализация продавца, HTTPS, реальные ограничения вместимости и доступности, резервное копирование, политика хранения и ротация токенов.

## Интерфейс, безопасность и наблюдаемость

На большом экране рядом находятся переписка и состав заказа, на телефоне итог и кнопка доступны в нижней панели. Изменённые позиции получают текстовую подпись и изменение суммы. Предоплата, полная стоимость и остаток показываются отдельно. Перед сдачей проверить фокус, клавиатуру, обе темы, контраст, reduced motion и экран шириной 360 px.

Права определяет сервер для каждого объекта и магазина. У владельца и покупателя отдельные разрешения. Cookie-сессии требуют CSRF-защиты для меняющих состояние запросов. Ответ модели валидируется по разрешённой схеме, а данные отображаются с экранированием. Ограничиваются длина сообщения, частота запросов и расход токенов. В журнале оставлять только технический ID, версию заказа, действие, задержку и результат. Для оценки стоимости учитывать токены и число вызовов модели на заказ. Проверки статуса оплаты не требуют вызова модели.
