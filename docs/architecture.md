# Архитектура конкурсного MVP

## Границы продукта

Один веб-сервис для продавцов с формализуемым прайсом. Три способа расчёта — фиксированная цена, сумма за единицу и тариф по диапазону. Готовая LLM работает без обучения на данных магазина. При индивидуальной смете агент передаёт менеджеру собранный черновик.

## Модули и полномочия

| Модуль | Ответственность |
| --- | --- |
| Веб-приложение | Сессия покупателя и сотрудника, карточка заказа, подтверждение суммы и управление каталогом |
| Агент | Из текущего черновика, сообщения и выбранных позиций формирует типизированное предложение изменений. Спрашивает недостающие сведения |
| Каталог и расчёт | Проверяет коды и количества, рассчитывает стоимость в копейках. Предоплата в процентах округляется до ближайшей копейки, при половине — вверх. Сохраняет снимок расчёта |
| Заказы | Применяет пакет правок одной транзакцией, проверяет версию и полномочия, хранит согласованный состав и привязку к магазину |
| Платежи | Регистрирует попытку для подтверждённой версии, обращается к MCP токеном нужного магазина, сохраняет внешний ID и сверяет результат |
| Аккаунты | Связывают способы входа и устройства с серверной историей. Права продавца проверяются отдельно для каждого магазина |
| Документы | Формируют подтверждение оплаты, хранят прикреплённый продавцом PDF и учитывают результат отправки через SMTP |
| Хранилище | SQLite на постоянном диске для одной реплики. В транзакциях проверяет уникальность активной попытки и повторов сообщений |

Целевой стек — Python, FastAPI, серверные HTML-шаблоны и небольшой браузерный JavaScript. Модули работают в одном процессе и используют явные границы доступа. Docker Compose запускает приложение на Linux-сервере с поддерживаемым образом и постоянным томом. База переживает пересоздание контейнера. Резервную копию SQLite формировать штатным механизмом согласованного снимка и проверять восстановление. Масштабирование на несколько записывающих реплик потребует другого хранилища или координации. Swagger UI работает в отдельном контейнере для просмотра клиентского контракта.

## Поток заказа

Покупатель отправляет сообщение с идентификатором повтора. Агент предлагает правку, сервер проверяет каталог и последнюю версию. Неоднозначность возвращает уточнение. Деньги рассчитывает приложение. При изменении прайса до подтверждения возвращается новая карточка заказа. У подтверждённой версии неизменяемые строки, суммы и доля предоплаты. Третье уточнение подряд переводит заказ на рассмотрение продавцу.

При подтверждении сервер атомарно создаёт запись попытки и фиксирует транзакцию до сетевого запроса. Сетевой вызов не удерживает блокировку базы. Единственный создатель попытки вызывает `create_payment` или `create_invoice` через MCP. При корректном ответе сохраняет внешний ID и проверенную ссылку при наличии. Сохранённая ссылка может быть возвращена повторно владельцу заказа. После обрыва с неизвестным результатом повторная отправка на создание блокируется до сверки у продавца. Для сверки в `description` передаётся уникальный идентификатор попытки без персональных данных.

Если агент передаёт заказ продавцу, открывается обращение с собственным идентификатором. Ответ сохраняется в истории. Покупатель снова уточняет состав перед оплатой. Пока модель обрабатывает сообщение или открыто обращение, сервер блокирует подтверждение. Старые открытые обращения восстанавливаются при первом запуске новой версии. Состояние исполнения хранится отдельно от платежа.

Сервер сверяет прямой платёж через `get_payment`. Для счёта он получает `get_invoice` и проверяет связанный платёж. В режиме оплаты по долям сервер сохраняет план и последовательно подтверждает каждую долю. После последней доли заказ становится оплаченным или получает статус предоплаты. При `pending` согласованный заказ остаётся закрытым для правок. Подтверждённая отмена позволяет повторить оплату текущей доли. [Статусы и сверка](api.md)

## Контракты и развёртывание

В базовом профиле новый продавец регистрируется по коду подключения. В закрытом профиле продавец создаёт витрину, назначенную администратором. Он публикует CSV по версии каталога и подключает собственный MCP-токен. Токен сначала проверяется через список инструментов, затем шифруется с привязкой к магазину. Серверный токен относится только к существующей кофейне. Существующие таблицы заказов сохраняются при добавлении таблиц кабинета. Гость получает отдельную cookie для каждой витрины. Вошедший покупатель получает доступ к заказам аккаунта с нескольких устройств. В закрытом профиле владельца истории определяет проверенная пара `issuer + subject`. [Синхронизация аккаунта](accounts.md)

Публичное HTTP API приложения описывает версии заказа, ошибки, авторизацию и повторы. Swagger UI открывает этот контракт. Отдельный серверный MCP-клиент подключается к официальному Streamable HTTP endpoint ЮKassa. Машиночитаемый контракт покрывает покупательские маршруты под `/api/v1`. Витрины, вход и кабинет используют веб-маршруты. Встроенная документация FastAPI выключена. Тест сверяет маршруты клиентского API с единой схемой. [Контракт и команды проверки](api.md)

Для готового релиза нужны воспроизводимая сборка приложения, один Compose-запуск без локального Python, непривилегированный пользователь, healthcheck и постоянный том. Тестовые секреты каждого магазина поступают из защищённой конфигурации. В README релиза указываются переменные без значений, способ проверки статуса, доступ к Swagger и сценарий восстановления после перезапуска. Для боевого использования проверяются фискализация продавца, HTTPS, реальные ограничения вместимости и доступности, резервное копирование, политика хранения и ротация токенов.

## Интерфейс, безопасность и наблюдаемость

На большом экране рядом находятся переписка и состав заказа, на телефоне итог и кнопка доступны в нижней панели. Изменённые позиции получают текстовую подпись и изменение суммы. Предоплата, полная стоимость и остаток показываются отдельно. Перед сдачей проверить фокус, клавиатуру, обе темы, контраст, reduced motion и экран шириной 360 px.

Права определяет сервер для каждого объекта и магазина. У владельца и покупателя отдельные разрешения. Cookie-сессии требуют CSRF-защиты для меняющих состояние запросов. Ответ модели валидируется по разрешённой схеме, а данные отображаются с экранированием. Ограничиваются длина сообщения, частота запросов и расход токенов. В журнале оставлять только технический ID, версию заказа, действие, задержку и результат. Для оценки стоимости учитывать токены и число вызовов модели на заказ. Проверки статуса оплаты не требуют вызова модели.
