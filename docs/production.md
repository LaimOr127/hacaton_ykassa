# Закрытое корпоративное развёртывание

## Кто может войти

Закрытый профиль рассчитан на сеть компании или VPN. Порт приложения не публикуется. Swagger отключён по умолчанию. Единственный опубликованный порт OAuth2 Proxy привязан к `127.0.0.1:4180`. Прокси организации принимает HTTPS на закрытом сетевом интерфейсе и передаёт трафик на этот порт. Публичной витрины в таком профиле нет. Покупатели входят через корпоративную учётную запись.

OAuth2 Proxy выполняет браузерный вход. Приложение отдельно проверяет подпись RS256 по JWKS, issuer, audience, срок жизни и подтверждённый адрес в домене компании. Заголовки с именем пользователя сами по себе доступ не открывают. Покупательские сессии связаны с `sub` учётной записи и конкретным магазином. Доступ к кабинету задаётся отображением `sub → магазин`, которое настраивает администратор. Код владельца работает в локальном режиме. В закрытом профиле используется корпоративный вход.

## Настройка администратора

1. Создайте конфиденциальное веб-приложение OIDC в IdP компании. Включите области `openid email profile`, подпись RS256 и выдачу `email_verified`. Зарегистрируйте точный callback `https://<внутреннее-имя>/oauth2/callback`. Ограничьте доступ корпоративной группой в настройках IdP.
2. В закрытой конфигурации задайте `PUBLIC_ORIGIN`, `OIDC_ISSUER`, `OIDC_JWKS_URL`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `OIDC_EMAIL_DOMAIN` и случайный `OIDC_COOKIE_SECRET` из 32 байт, кодированных URL-safe Base64. Установите `OIDC_COOKIE_EXPIRE` не дольше срока ID-токена. Пример поля ролей — `OIDC_MERCHANTS_JSON='{"subject-из-IdP":"coffee"}'`. Subject берётся у администратора IdP. Email не используется как ключ назначения владельца.
3. Задайте `MERCHANT_VAULT_KEY` и перенесите его в резервное хранилище секретов. Ограничьте доступ к файлу переменных, постоянному тому и Docker daemon. Для провайдера компании настройте доверенный HTTPS-адрес `LLM_BASE_URL` и `LLM_MODEL`. До живой проверки оставьте `APP_MODE=simulated`.
4. На HTTPS-прокси сохраните Host и передавайте корректный HTTPS-схемный заголовок. Перезаписывайте поступающие клиентские `X-Forwarded-*`. Разрешите обращения к прокси только из VPN или сети компании. Убедитесь, что порт 4180 остаётся на loopback.

```sh
docker compose -p orders-company -f compose.yaml -f compose.private.yaml config --quiet
docker compose -p orders-company -f compose.yaml -f compose.private.yaml up --build -d
docker compose -p orders-company -f compose.yaml -f compose.private.yaml ps
```

Используйте Docker Engine 28 или новее и Compose 2.24.4 или новее. Укажите отдельное имя проекта. До включения трафика проверьте с другой машины, что порт 4180 недоступен, а HTTPS доступен через разрешённую сеть. Проверьте вход с обычным сотрудником, назначенным владельцем, сотрудником без роли продавца и учётной записью вне разрешённого домена. Перенос в другую компанию требует своего клиента IdP, токенов магазинов, постоянного тома и политики сети.

## Коннекторы и профили

| Коннектор | Что делает владелец в кабинете | Что проверяет сервер |
| --- | --- | --- |
| Корпоративная учётная запись | Входит через привычный IdP, открывает назначенную витрину | Подписанный ID-токен, домен и назначение конкретного `sub` |
| Языковая модель | Выбирает OpenAI или корпоративный совместимый API, вставляет API-ключ, загружает список доступных моделей и выбирает модель. Можно задать название вручную | Адрес берётся из доверенной настройки, а не из формы. Перед сохранением проверяется структурированный ответ. Ключ шифруется с привязкой к продавцу, провайдеру, адресу и модели |
| ЮKassa | Вводит MCP-токен магазина в разделе «Оплата» | Тест подключения проверяет доступ к `create_payment` и `get_payment`. В рабочем сценарии токен выбирается только для нужного продавца |

Раздел модели умеет заменять и отключать подключение. После отключения или ошибки расшифровки сервис прекращает вызовы для этого магазина. API-ключи не выводятся обратно в интерфейс. Список моделей зависит от того, что возвращает API провайдера для конкретного ключа. Для отдельных API выбор модели вручную возможен, если у них отсутствует список.

Вход через IdP открывает витрину и назначенный кабинет. Подключение модели через аккаунт OpenRouter доступно при `OPENROUTER_OAUTH_ENABLED=1`, настроенном хранилище ключей и `APP_MODE=live`. Владелец подтверждает доступ на сайте провайдера. Приложение получает отдельный ключ через PKCE, проверяет выбранную модель и шифрует ключ. По умолчанию на форме OpenRouter предлагается лимит $1 и срок 7 дней. Владелец проверяет эти параметры перед подтверждением. Модель можно сменить через кабинет. Личные агенты и подписки ChatGPT этим способом не импортируются. [Авторизация OpenRouter](https://openrouter.ai/docs/guides/overview/auth/oauth)

Веб-адрес возврата `PUBLIC_ORIGIN/merchant/model/openrouter/callback` должен быть доступен из браузера сотрудника. Для локальной проверки используйте `http://localhost:8000`, для компании HTTPS. Исключите строку запроса этого пути из access-логов обратного прокси. Встроенный Uvicorn в Compose не пишет access-логи.

Владелец заменяет платёжный токен в разделе «Оплата». Сначала завершите все активные попытки оплаты и сверки. Приложение проверяет доступ к инструментам MCP и запрашивает известный завершённый платёж этого магазина. Идентификатор, сумма, валюта и описание попытки должны совпасть. До успешной проверки старый токен остаётся действующим. Если в журнале ещё нет подходящего платежа, сохраняйте доступ к прежнему токену и обратитесь к администратору развёртывания.

Кнопка «Проверить инструменты ЮKassa» показывает результат `tools/list` для токена магазина. Включайте `MCP_INVOICES_ENABLED=1` для развёртывания с поддержкой счетов у всех подключённых магазинов. ЮKassa не выставляет счета из тестового магазина. Все платежи и счета создаются после отдельного подтверждения суммы покупателем. [Инструменты и параметры](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/mcp-server/tools) · [Тестовый магазин](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/mcp-server/quick-start)

## Настройки оплаты и документы

В «Настройках оплаты» у магазина четыре независимых переключателя. Разделение и чаевые действуют для прямой оплаты. Платёж каждой доли идёт на счёт магазина, на который подключён MCP-токен. Остаток за услуги при предоплате сохраняется отдельно. Владелец заказа может переслать текущую ссылку ЮKassa, а следующую получает после подтверждения предыдущей доли.

Продавец может прикрепить PDF кассового чека размером до 512 КБ к подтверждённому платежу. Для каждой оплаченной доли приложение также формирует справочное подтверждение. Чек выдаёт продавец через свою фискальную систему. Получение и отправка фискальных чеков через инструменты MCP отсутствуют. [Возможности MCP](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/mcp-server/basics)

Для почты администратор указывает `MAIL_SMTP_HOST`, `MAIL_SMTP_PORT` и `MAIL_FROM`. Если сервер требует вход, заполняет `MAIL_SMTP_USER` и `MAIL_SMTP_PASSWORD`. Используется SMTP с TLS с начала соединения, стандартный порт 465. Покупатель явно выбирает документ и вводит email. Адрес не хранится в открытом виде. В течение 7 дней повтор для того же документа и адреса возвращает сохранённый статус доставленного или неопределённого письма. После подтверждённого отказа можно повторить запрос через минуту. Заменённый PDF можно отправить как новую версию. В симуляции внешние письма отключены. Подтвердите приём письма почтовым сервером компании до использования с реальными заказами.

Перед откатом на версию без долей выключите разделение и чаевые и завершите начатые планы. Пока оплаченная часть требует сверки, используйте текущую версию. Защита в базе блокирует перевод неполностью оплаченного плана в конечный статус старым кодом.

## Нагрузка и масштабирование

Настройки по умолчанию дают 25 обращений к модели за час на сессию, 60 на магазин и 120 на экземпляр. Допускается 8 одновременных вызовов модели и 128 одновременных соединений и задач на уровне Uvicorn. Настройки модели доступны через переменные `MODEL_*`. При трёх сообщениях на оплаченный заказ один магазин получит максимум 20 таких заказов в час, весь экземпляр — до 40. Это потолок по квоте. Фактические показатели зависят от числа уточнений, доступности провайдеров и задержек.

Нагрузочный сценарий проходит создание заказа, два сообщения, создание платежа, повтор с тем же ключом и подтверждение симуляции. Замер выполнен на Windows, один процесс Uvicorn, локальная SQLite и HTTP по loopback.

| Параллельных клиентов | Завершено | Заказов/с | p95 полного заказа |
| ---: | ---: | ---: | ---: |
| 8 | 100 из 100 | 3,73 | 2,50 с |
| 24 | 100 из 100 | 3,87 | 6,68 с |

Числа характеризуют локальную симуляцию. Для повтора используйте отдельную базу и команду `python scripts/checkout_load.py --users 100 --concurrency 24`. При выборе мощности проверьте нагрузку компании и задержки IdP, провайдера модели и ЮKassa. Текущий профиль рассчитан на один записывающий процесс. Для горизонтального запуска потребуются общее хранилище и общие лимиты. При переносе на PostgreSQL сохраните уникальность активного платежа, проверки версии, транзакционную идемпотентность и разделение магазинов.

Из базы нагрузочного прогона восстановлены 200 оплаченных заказов и 200 соответствующих платёжных попыток. Проверки целостности SQLite и внешних ключей прошли. Процедуру нужно повторить на резервной копии компании.

## До допуска к рабочим данным

Проведите живой вход через IdP и пройдите контрольное отключение учётной записи. Проверьте разрешённые API модели и тестовые магазины каждого продавца. Прогоните нагрузку и восстановление резервной копии на отдельном экземпляре. Для боевой ЮKassa проверьте фискализацию и доступность чеков вне MCP. Границы и проверки окружения задокументированы в инструкции обслуживания.
