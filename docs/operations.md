# Запуск и обслуживание

## Подготовка сервера

1. Используйте сервер с Docker Engine и Compose v2. Приложению требуется один записывающий экземпляр и постоянный том `order_data`. Базовый Compose публикует приложение на `127.0.0.1:8000` и Swagger на `127.0.0.1:8081`.
2. Для рабочего доступа используйте закрытый профиль и HTTPS-прокси из VPN или сети компании. Сохраните внешний Host для проверки Origin. Swagger в закрытом профиле выключен по умолчанию. [Инструкция для рабочего контура](production.md)
3. Храните `.env` и резервные копии базы отдельно от Git. Сохраните копию `MERCHANT_VAULT_KEY` в защищённом хранилище. Она понадобится для расшифровки токенов после переноса.
4. Сначала запустите симуляцию и проверьте кофейню и клининг. Затем при наличии доступов включите `APP_MODE=live` и подключите именно тестовые магазины. Два режима используют отдельные файлы SQLite.

Команды базового профиля для холодного запуска и проверки на Linux.

```sh
docker compose up --build -d --wait
docker compose ps
docker compose logs --tail 50 app
curl -fsS http://127.0.0.1:8000/healthz
```

Лимиты по умолчанию — 25 запросов на сессию, 60 на магазин и 120 на экземпляр за час. Оплата не вызывает языковую модель. Для расширения лимитов сначала измерьте число обращений, тайм-ауты и стоимость. SQLite рассчитана на одну записывающую реплику.

## Согласованная резервная копия

SQLite создаёт согласованный снимок через backup API. Следующая команда для Linux пишет новый файл с уникальным именем и проверяет его целостность. Для закрытого профиля в командах `exec` и `cp` используйте те же параметры `-p` и `-f`, с которыми запустили контейнер.

```sh
docker compose exec -T app python -c 'import os, sqlite3, time; from pathlib import Path; p=Path(os.environ["DATABASE_PATH"]); dst=p.with_name("backup-"+str(time.time_ns())+".sqlite3"); a=sqlite3.connect(f"file:{p}?mode=ro",uri=True); b=sqlite3.connect(dst); a.backup(b); assert b.execute("PRAGMA integrity_check").fetchone()[0]=="ok"; b.close(); a.close(); print(dst)'
```

Скопируйте напечатанный файл с помощью `docker compose cp app:/data/backup-…sqlite3 ./` в отдельное защищённое хранилище. База содержит сведения о заказах и переписку. Ключ хранилища токенов переносится отдельно.

Для проверки восстановления запустите отдельный экземпляр с копией базы и уникальным Compose-томом. Пройдите сверку истории заказов и платёжных попыток на тестовом окружении. После этого запланируйте переключение. При откате версии кода сохраняйте платежный журнал и проверяйте совместимость схемы.

## Если платёж остаётся неизвестным

Откройте «Сверка платежей» в кабинете продавца. Для прямого платежа можно запустить поиск в пределах времени попытки или указать известный ID. Для счёта без известного ID введите его из кабинета ЮKassa. Пока исход неизвестен, существующая попытка блокирует повторную оплату. Обычный `pending` сверяется в фоне. Продавец может проверить его прямо из карточки заказа. Сбои внешних подключений отображаются в кабинете и пишутся в технический журнал контейнера. [HTTP API и восстановление](api.md)

Для перехода к приёму реальных платежей нужны проверка режима магазина, настройка чеков, сроки хранения данных и подтверждённое восстановление резервных копий. MCP-процесс приложения ведёт разовый платёж. [Ограничения MCP ЮKassa](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/mcp-server/basics)
