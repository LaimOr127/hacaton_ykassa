# Работа над «Заказом из переписки»

Прочитай README.md, PLAN.md и docs/architecture.md. Перед изменением контрактов проверь схему в contracts/ и инструкцию docs/api.md, когда они доступны. Общайся по-русски. Сверяй утверждения о готовности с файлами, тестами и состоянием Git.

## Роли

- **Astra 6.2** проектирует архитектуру и проверяет реализованные решения, ищет ошибки и регрессии. Может вести архитектурную документацию и координировать ветки.
- **Sol 6.2** пишет и исправляет код, тесты, Docker, CI, хуки и машиночитаемые контракты.
- **Terra 6.2** выполняет поиск в интернете. Если запрошенная модель недоступна, укажи ограничение. Для текущих задач используй уже проверенные источники в документации, когда их достаточно. Самостоятельно подменять модель другой версией нельзя.

## Разработка

1. Проверь активную ветку, изменения пользователя и удалённую базу. Выбери ближайший незавершённый этап из PLAN.md.
2. Пиши минимальное законченное изменение. По задаче используй Ponytail, затем Ponytail Review. Для интерфейса — Frontend Design и проверку доступности. Для API и платежей — API Design и Security Best Practices. Для контейнеров — Docker Patterns. Загружай только применимые навыки.
3. Для проверки правил и сумм используй воспроизводимые примеры из плана. Финансовый результат определяет сервер. Модель получает только данные одного магазина и текущего заказа. Секреты и платёжные ссылки не входят в промпты, логи или git.
4. До коммита проверь содержимое staged diff, пробелы, отсутствие секретов и подходящие тесты. В конкурсной реализации ввести быстрые локальные хуки для lint, схем и секретов, тяжёлые тесты и холодный запуск Compose выполнять в CI. Не отмечай запланированный хук как установленный.
5. Обнови состояние и следующий шаг в PLAN.md. В документации различай черновик контракта, проверенный код, симуляцию и работу с тестовым MCP.
6. При изменении корпоративного входа или коннекторов сверяйся с [закрытым профилем](docs/production.md). При изменении записи в хранилище прогоняй локальный сценарий `scripts/checkout_load.py` на отдельной симулированной базе.

## Git

Основная ветка — main. Для завершённой возможности используй тематическую ветку и обычный push. Имя и email бери из подтверждённой конфигурации автора. По завершении проверки сливай ветку в основную с merge-коммитом (--no-ff), сохраняй историю и проверяй SHA на origin. Не включай посторонние файлы, не используй force push и не переписывай конкурсные даты.

Откат опубликованного этапа оформляется в новой ветке через git revert -m 1 для соответствующего merge-коммита. После тестов слей этот откат обычным merge. Если появилась миграция данных, до отката проверь совместимость формата базы и резервную копию. Сохраняй платёжный журнал.
